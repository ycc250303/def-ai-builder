# 单人植物养护第一版：需求确认

更新：2026-11-14。本文给非技术人员确认第一版做什么、做到什么程度算完成。标为「建议」的内容还没有最终定稿。实现方式见 [技术选型说明](./technology-selection.md)。

## 1. 产品要解决什么

面向自己养植物的人，帮助他们弄清四件事：我的植物现在怎么样、接下来该做什么、以前做过什么、最近有什么变化。

使用过程：

建立植物档案 → 查看环境情况 → 收到提醒 → 记下养护 → 向助手提问 → 查看一段时间的总结。

已经确定：

- 需要联网。助手可以使用远程服务。
- 一个人单独使用。需要用账号和密码注册登录。自己的内容保存在网上，重新打开或换一台设备后还能看到。
- 环境数据先用模拟数据。传感器型号和真实测量能力还没定。
- 包含植物监测、养护记录、植物主页、智能问答、照片辅助分析和阶段总结。
- 不做音乐、社交、多人一起养护，也不连接真实硬件。这一版不出现音乐设置。

一个人使用，是指用户之间没有互动。一个账号可以管理多株植物。每个账号只能看到自己的植物、照片、对话和设备。

## 2. 第一版必须完成的功能

### 2.1 植物档案与主页

- 可以新建、查看列表、查看详情、修改、删除自己的植物。植物主页展示完整档案，并提供编辑和删除入口。
- 昵称和品种分开。用户起的名字不等于植物种类。种类要对应到标准名称和养护资料。
- 可以记录种植日期。不知道种植日期时可以留空，改记「开始养护日期」。把植物加入应用的时间不能当成植物的真实年龄。
- 可以放照片、填写摆放位置，也可以写一段个性描述。个性描述只影响展示或对话语气，不改变养护判断。
- 主页显示当前状态、最近更新时间、需要关注的提醒、最近一次养护，以及向助手提问的入口。
- 快捷操作至少包括：记录浇水、添加养护记录、询问助手。

培养地支持室内、室外，培养方式支持土培、水培，均可留空。花盆和基质说明属于后续养护功能。水培植物不能套用土壤干湿规则。

完成后：能创建一株植物，刷新或重新登录后还能找到它，并在同一个主页看到状态、记录，以及进入提问。

### 2.2 环境情况与历史

先模拟四类常见数据：

- 土壤干湿：用 0 到 100 的「模拟土壤含水指数」表示相对干湿。这个数字用于演示，不能当成经过标定的真实含水量，也不能当成空气湿度。
- 光照：单位为勒克斯，测的是传感器所在位置的亮度，不能直接当成叶子吸收了多少光。
- 空气温度：单位为摄氏度。
- 空气湿度：用相对湿度的百分比表示。

每条数据带上采集时间、收到时间、来源、单位，以及这条数据是否可用。至少要能看出三种情况：有效、缺失、过期。以后换成真实设备时，还要能记下这套数据有没有经过标定。

- 显示最新读数和最后更新时间。没有数据时不能显示成 0。
- 显示历史曲线和变化趋势。建议先提供最近 24 小时和最近 7 天。
- 趋势由系统事先算好再展示，例如平均水平、高低范围、正在变干还是变湿。不要求助手逐条重算原始数据。
- 没有数据或连接中断时，要明确告诉用户。不能把以前的旧数据继续标成刚刚测到的。
- 这一版不展示植物电信号、营养含量、酸碱度、叶绿素或健康评分。这些目前没有确定的采集依据。

完成后：可以切换正常、缺水、白天光照偏低、断连或缺少数据等场景。当前数字和历史曲线来自同一份数据，刷新后仍然一致。

### 2.3 基础提醒

- 根据植物资料、有效的环境数据和养护记录，提醒「检查是否需要浇水」「近期光照可能不足」等。
- 某一品种已有可靠规则时，可以增加温度异常等简单提醒。
- 是否提醒由固定规则决定，同一种情况每次结果相同。助手负责解释、追问和建议，不负责每次临时决定要不要提醒。
- 判断光照要看白天的时段、亮度和持续了多久。晚上天黑不能触发缺光提醒。
- 判断土壤要结合种植介质、最近一次浇水，以及这种状态持续了多久。某一个瞬间的读数不能直接触发「马上浇水」。
- 提醒要能区分：刚出现、已读或已处理、问题已恢复、用户关闭。同一个问题一直存在时，不要反复弹出。
- 这一版只控制应用里的提醒。系统推送、邮件和短信没有被要求，这一版不做。

园艺资料里的「明亮散射光」「两次浇水之间让土干一干」，不能直接换成一个所有植物通用的亮度或湿度数字。第一版如果只用演示用的数字，页面上要标明这是演示规则。等传感器和种植介质确定后，再调整这些数字。

完成后：同一段数据重复判断，提醒结果相同。夜晚、断连、缺少数据时，不会给出误导性的养护指令。问题恢复后，提醒状态跟着更新。

### 2.4 养护记录

- 可以记录浇水、施肥、换盆、修剪、照片观察和自由备注。优先做好浇水、换盆、照片和备注。
- 时间和事件类型要填写。备注可以写。水量可以不填，不要求用户凭空估计浇了多少。
- 可以补记以前发生的事，也可以修改和删除。时间线按事情实际发生的时间排列。
- 显示距离上次浇水多久、已经养护了多少天。这些由系统计算。
- 用户点「已浇水」，只表示用户记下自己浇过水，不表示传感器已经测到土壤变湿。
- 在模拟场景里，浇水之后可以让土壤变湿，然后再慢慢变干。这只出现在模拟数据中。

完成后：一次浇水会同时出现在时间线、最近浇水时间，以及之后向助手提问时能用到的信息里。修改记录后，这些结果一起更新。

### 2.5 智能问答与建议

对话针对当前这株植物。回答综合这些信息：

- 已确认的品种和可靠的养护资料。
- 当前有效数据、数据是模拟还是实测、更新时间。
- 近期变化摘要和已有提醒。
- 养护记录、摆放位置和用户补充的描述。

回答按这个顺序说清楚：看到了什么、可能是什么原因、建议怎么做、还需要确认什么、资料从哪里来。规则产生的提醒、用户自己记下的事实、助手的推断，要能分得清。

- 能回答「今天需要浇水吗」「为什么最近叶子发黄」「应该换个位置吗」这类具体问题。
- 模拟数据要说明是模拟的，不能说成真实测量。没有来源或数据过期时，要说明依据不足。
- 不能把昵称或个性描述当成品种知识。
- 对话要保存，以后可以回看。助手暂时不能用时，监测、规则提醒和已有记录仍然可以看。
- 助手的一次建议不能自动记成「已经浇水」。只有用户确认并自己记下，这件事才算发生过。

完成后：换一株植物、补一条浇水记录，或切换数据场景后，回答能体现这些变化。引用的资料要能对上实际查到的条目，不能编造出处。

### 2.6 照片辅助分析

- 可以上传或拍摄植物照片，结合这株植物的档案、环境数据和养护记录，帮助分析异常。
- 结果包括：照片上能看到什么、几种可能原因、下一步检查什么、可以怎么处理。证据不够时，请用户补充叶片背面、整株、土壤等照片，或补充养护信息。
- 叶子发黄、有斑点、发蔫可能有很多原因。一张照片不能直接当成已经确诊某种病害。
- 分析结果可以存进成长记录。再次查看时，保留照片、时间、用户描述和分析依据。
- 用照片识别品种可以作为以后的增强。这一版必须做的是异常辅助分析。创建档案时，用户先在一个小型植物目录里自己选择品种。自动识别不是每一步的前提。

完成后：可以完成上传、查看分析、阅读建议、保存记录。照片无关或太模糊时，给出合理提示，不编造确定诊断。

### 2.7 一段时间的总结

- 按用户选定的时间段生成养护总结。建议先做用户主动查看的周报，不要求系统按时自动发送。
- 系统先统计：这段时间有多少数据、缺了多少、温湿度范围、光照变化、提醒次数、养护次数。助手再根据这些统计来解释。
- 要说明总结覆盖了哪一段时间、实际收到了多少数据。时间跨了 7 天但只收到少量读数时，不能写成连续监测了 7 天。
- 说明观察到的变化，以及下一阶段该关注什么。没有照片或生长测量时，不能写成「长高了」「长出新叶」或「根系恢复了」。
- 可以用标明为模拟的历史数据来演示长期总结。不能把演示用的历史说成用户真实种过的经历。

完成后：总结里的浇水次数、时间范围和关键数字，与系统统计一致，并能在记录和曲线里核对。

### 2.8 账号、虚拟设备与数据保存

- 用账号和密码完成注册、登录、退出，并在下次打开时恢复登录。不需要邮箱、短信或第三方账号。一个账号管理自己的植物和记录。
- 植物、照片、对话和设备都属于对应账号。
- 可以绑定、命名、解绑一个虚拟花盆，并把它关联到一株植物。一个设备同一时间只对应当前绑定的那株植物。以前的测量仍归当时绑定的那株植物。
- 显示模拟的连接状态、最后同步时间，以及数据从哪里来。
- 这一版的网络相关内容，只涉及应用能否联网，以及模拟设备是否在线。真实的无线配网、蓝牙查找设备和固件升级先不做。
- 档案、养护记录、历史数据和对话保存在网上。刷新、重新登录或换一个浏览器后可以恢复。这一版先不做离线修改后再合并。
- 隐私说明至少要告诉用户：照片和聊天会被发给助手服务。并提供删除相关记录和用户数据的办法。具体保存哪些内容，随功能做出来时写清楚。

完成后：登录后能看到自己的数据。解绑设备不会改掉历史记录。应用断网时能说明当前状态。应用连得上服务器，不等于模拟设备在线。

## 3. 模拟数据要能演示的情况

四项数据要连在一起变化，方便看懂发生了什么：

- 正常的一天：白天亮、晚上暗，温度和空气湿度在合理范围里变化，土壤慢慢变干。
- 缺水：土壤持续变干，可以触发检查提醒。
- 刚浇水：用户记下浇水后，模拟数据里水分上升，然后再慢慢下降。
- 光照不足：连续几个白天的亮度都不够。只把某一个瞬间调低，不算这个场景。
- 数据出问题：设备离线、某一个数据缺失、读数过期，或突然出现一个不合理的尖峰。

同一套场景要能重复演示，方便核对。页面和提醒根据整理好的观测结果来显示。具体设备和传输方式以后再定。

## 4. 建议包含的页面

下面是信息怎么组织的建议，最终界面还没定：

1. 登录和注册。
2. 我的植物，以及新建档案。
3. 植物主页：状态、提醒、最近记录、快捷操作。
4. 环境详情：历史曲线和趋势。
5. 养护记录：时间线、补记和照片。
6. 助手：问答、照片分析、阶段总结，都围绕当前这株植物。
7. 设备与设置：虚拟设备、连接状态、同步、通知和隐私。

## 5. 当前先做的四步

顺序已经确定：把应用和后台连通 → 账号密码注册登录 → 录入植物档案 → 整理权威植物资料并保存在项目里。账号密码注册登录、植物档案录入和档案主页已经完成。

### 第一步：把应用和后台连通

- 手机应用能打开，支持 iOS 和 Android。
- 后台能启动，并能连上数据库。
- 准备一份不含真实密码的配置示例和启动说明。真实密码不放进项目。
- 做一个用来确认连通的后台接口，让应用能实际拿到后台返回的内容。
- 完成后：应用能启动，后台能启动并连上数据库，应用能显示后台返回的内容。还没验证过的运行环境要单独说明。

### 第二步：账号密码注册登录

这一步已经完成。确认过的要求如下：

- 可以注册、登录、退出、查看当前是谁，并在下次打开时恢复登录。不使用邮箱或短信验证。
- 登录页提供「忘记密码」。填写账号名称和新密码后提交，成功时返回登录并提示使用新密码登录。
- 密码重置仅凭账号名称定位账号，无其他身份验证；知道账号名称的人可以重置该账号的密码。
- 账号有长度和允许使用的字符。大小写不同、实际是同一个名字时，算同一个账号。同一个账号不能注册两次。
- 密码加密保存。输入密码时，不偷偷改掉用户本来输入的内容。
- 两个人同时用同一个名字注册，只有一个成功，另一个看到「账号已占用」。
- 没登录不能查看用户数据。登录状态保持 7 天。退出后，这次登录立刻失效。
- 密码重置成功后，旧密码和现有登录令牌失效；新密码保留原文内容，长度为 8 到 64 位。重置失败时保留表单输入并显示原因。
- 完成后：注册后可以登录；重复账号被拒绝；密码错误时登录失败；没登录不能查看用户数据；退出后这次登录失效。

密码重置接口为 `POST /users/reset-password`，允许匿名访问，请求字段如下：

```json
{"username": "alice", "newPassword": "new-password"}
```

账号名称使用注册时的大小写和首尾空白规范化规则。成功返回 HTTP 200，响应正文为空。账号名称不合法返回 HTTP 400 / `INVALID_ACCOUNT`；密码不合法返回 HTTP 400 / `INVALID_PASSWORD`；账号不存在返回 HTTP 401 / `ACCOUNT_NOT_FOUND`；请求正文缺失或无法解析返回 HTTP 400 / `INVALID_CREDENTIALS`，均使用 Problem Details。数据库或登录存储不可用返回 HTTP 503 / `DATA_STORE_UNAVAILABLE`，删除登录令牌失败时回滚密码更新。登录和密码重置按同一账号顺序执行。

### 第三步：录入植物档案

- 可以创建、查看列表、查看详情、修改和删除。植物属于当前登录的人。
- 品种必填，去除首尾空白后最多 100 字。昵称选填，最多 100 字，留空时使用本次填写的品种名称。
- 种植日期选填；开始养护日期选填，留空时使用上海时区的当天日期。日期格式为 `yyyy-MM-dd`。
- 培养地选填，室内或室外；培养方式选填，土培或水培。简要描述选填，最多 1000 字。
- 新建和更新共用完整表单。更新时选填内容可以清空，昵称和开始养护日期留空时应用相同默认值。
- 表单使用红色「*」标记必填品种，其他字段直接显示名称。
- 这一步先从示例品种里选择，或自己填写名称。可以填写未知品种。不依赖真实传感器、照片识别或外部资料接口。
- 先按用户填写的文字保存品种。下一步资料目录做好后，再由用户明确选择对应的标准物种。用户随手填写的文字，不能直接当成已经核对过的分类结果。
- 示例植物也真实保存。退出并重新登录后仍能看到。
- 完成后：用户可以管理自己的多株植物。其他账号不能查看、修改或删除这些植物。日期未知时也能保存。

已实现的接口均需要登录，档案归属从当前登录身份取得。查询、更新、删除同时限定植物编号和所属用户；其他账号访问返回「植物不存在」。更新和删除各使用单条数据库语句，重复删除返回不存在，更新与删除并发不会重新创建档案。

| 操作 | 接口 | 返回 |
| --- | --- | --- |
| 查看自己的植物列表 | `GET /plants` | 按编号倒序排列的档案数组 |
| 查看植物主页档案 | `GET /plants/{id}` | 完整档案 |
| 新建植物档案 | `POST /plants` | 保存后的完整档案 |
| 更新植物档案 | `PUT /plants/{id}` | 完整替换后的档案 |
| 删除植物档案 | `DELETE /plants/{id}` | 成功时 HTTP 200，响应正文为空 |

接口字段为 `id`、`nickname`、`species`、`plantingDate`、`careStartDate`、`growingLocation`、`cultivationMethod`、`description`。输入中不包含 `id`。培养地使用 `INDOOR` / `OUTDOOR`，培养方式使用 `SOIL` / `WATER`，未填写的选项使用 `null`。输入不合法返回 HTTP 400 / `INVALID_PLANT_INFO`；植物不存在返回 HTTP 404 / `PLANT_NOT_FOUND`，均使用 Problem Details。

### 第四步：整理权威植物资料并保存在项目里

- 查看来源和能不能使用，可以和前面几步同时进行。正式整理和导入在这一步完成。
- 先覆盖大约 5 到 10 种常见室内植物。具体名单在整理时确定。不把全世界所有植物一次导入作为开工条件。
- 物种名称和分类优先查可以下载的权威名录。养护知识结合大学推广机构或园艺机构的资料，逐条确认适合什么情况、能不能再用。
- 资料以结构化文件保存在项目里，并能重复导入。重复导入不会把同一条资料添加多次。
- 每条资料保存来源名称、链接、版本或查看日期、使用许可和必要的署名。权威来源的原文，和本项目整理、翻译或由模型写出的文字，要分开标记。
- 许可明确允许保存和再次分发的资料，可以放进项目。授权不清楚的正文和图片只保留引用信息，不整段复制进来。
- 完成后：能核对出处；重复导入不会产生重复条目；可以按标准物种查到分类和养护信息；授权没确认或缺失的部分有明确标记。

这四步完成后，再做环境数据模拟、曲线、规则提醒、养护记录、智能问答、照片分析和阶段总结。这些功能仍在第一版范围内。
