# 单人植物养护 MVP：需求基线

更新：2026-11-12。依据：本次用户说明、用户对「可联网的单人 MVP，账号与同步保留简化版」的确认，以及 Figma 中的植物养护、植物主页和用户设备模块。

本文区分已确认范围与实施建议；实施建议尚不代表技术选型或最终交互已确定。当前任务是理解需求与参考产品，尚未开始应用开发。

## 1. 产品目标与边界

面向个人植物主人，帮助其了解「我的植物现在怎样、应该做什么、做过什么、最近有什么变化」。第一版以真实植物的养护闭环为核心：

建立植物档案 → 查看环境数据 → 收到基础提醒 → 完成并记录养护 → 向 AI 询问原因和做法 → 查看阶段总结。

已确认：

- 可联网；AI 可以调用远程服务。
- 单人独立使用；注册登录、简化数据同步保留。
- 传感器数据来自 mock；硬件型号、协议和最终测量能力未定。
- 包含植物监测、养护记录、植物主页、AI 问答、照片异常辅助分析及长期总结。
- 不实现音乐、社交、多人协作或真实硬件接入；本版不展示音乐设置。

单人指没有用户间互动，不限制一个用户管理多株植物，也不等同于完全离线或无后端。

## 2. 必须完成的能力

### 2.1 植物档案与主页

- 新建、查看、编辑、删除自己的植物档案；首版建议以少量常见室内盆栽为支持范围。
- 名称与品种分开：用户给植物起的昵称，不等于植物物种；物种需要关联标准学名与知识条目。
- 记录种植日期；不知道种植日期时允许留空并使用「开始养护日期」，不能把加入 App 的时间当作实际植物年龄。
- 保留照片、摆放位置和可选的个性描述；个性只是展示或对话语气信息，不影响养护事实与规则。
- 主页显示当前状态、最近更新时间、需关注的提醒、最近养护事件、AI 建议入口。
- 快捷操作至少包含「记录浇水」「添加养护记录」「询问 AI」。

建议保留的上下文包括：室内/室外、土培/水培、盆器与基质简述。第一版可以主要支持室内土培，但不能对水培植物套用土壤湿度规则。

验收：用户能创建一株植物，刷新或重新登录后仍能找到它，并从同一主页查看状态、记事和进入 AI 会话。

### 2.2 环境监测与历史

先模拟通常容易通过常见传感器获取的四类数据：

- 土壤含水情况：使用明确命名的「模拟土壤含水指数」，可用 0–100 表示相对干湿；这不是经标定的体积含水率，也不是空气相对湿度。
- 环境光照：照度，单位 lux；属于传感器位置的测量值，不直接等于叶片吸收光量。
- 空气温度：单位 °C。
- 空气相对湿度：单位 %RH。

每个数据点携带采集时间、接收时间、来源（mock / 后续真实设备）、单位与质量状态。质量状态至少能区分有效、缺失、过期；未标定信息在替换为真实设备时也有位置可记录。

- 展示最新读数及最后更新时间；缺失值不能当作 0。
- 展示历史曲线及变化趋势；建议先支持近 24 小时和近 7 天。
- 趋势由程序计算，例如均值、范围、变化方向；不需要让 AI 逐条计算原始数据。
- 无数据和断连时明确显示状态，不能继续把旧值标成实时。
- 现阶段不生成植物电信号、营养含量、pH、叶绿素或健康评分等没有确定采集依据的数值。

验收：正常、缺水、白天光照偏低、断连/缺数据等场景可切换；当前数值与历史曲线来自同一套数据，刷新后保持一致。

### 2.3 基础提醒

- 基于植物资料、有效环境数据和养护记录，产生「检查是否需要浇水」「近期光照可能不足」等基础提醒。
- 可增加温度异常等简单提醒，前提是存在有依据的物种规则。
- 规则由普通程序稳定执行；AI 负责解释、追问与建议，不负责每次随机决定是否触发提醒。
- 光照判断结合白天时段、强度和持续时间，不能因晚上照度低就报缺光。
- 土壤读数需结合介质、最近浇水及持续时间，避免单个瞬时值直接触发「立即浇水」。
- 提醒具有触发、已读/已处理、恢复或关闭等状态；同一持续问题不反复刷屏。
- 通知设置先控制站内提醒；系统推送、邮件、短信渠道未被本次需求指定，不自动扩展实现范围。

重要区分：文献或园艺资料中的「明亮散射光」「两次浇水间让介质干燥」不等于某个通用 lux 或湿度百分比。MVP 的数值阈值若只是演示配置，需要标为演示规则；后续传感器与基质确定后再校准。

验收：同一段数据重复评估得到一致提醒；夜晚、断连与缺数据不会产生误导性养护指令；问题恢复后状态更新。

### 2.4 养护事件与成长记录

- 记录浇水、施肥、换盆、修剪、照片观察和自由备注；以浇水、换盆、照片与备注优先。
- 时间、事件类型、备注为基础；水量允许选填，不强迫用户凭空估计。
- 支持补记过去事件、修改和删除；按实际发生时间展示时间线。
- 展示距上次浇水多久、已养护天数等程序计算结果。
- 日志与传感器测量分开：点击「已浇水」是用户记录，不证明探头已经测到水分变化。
- 在 mock 场景中，可以显式模拟浇水后湿度上升；这只是模拟器行为。

验收：一次浇水记录同时反映在时间线、最近浇水时间和后续 AI 上下文中；编辑记录后相关结果正确更新。

### 2.5 AI 养护问答与建议

会话绑定当前植物。回答应综合：

- 已确认的品种与可信养护知识。
- 当前有效数据、测量/模拟来源与更新时间。
- 近期数据摘要和已有提醒。
- 养护事件、摆放位置和用户补充描述。

建议的输出结构是「观察到的情况 → 可能原因 → 建议操作 → 仍需确认的信息 → 资料来源」。规则提醒、用户事实和模型推断要能区分。

- 支持「今天需要浇水吗」「为什么最近叶子发黄」「应该换个位置吗」等具体问题。
- 不把模拟数据表述成真实观测；来源缺失或数据过期时说明依据不足。
- 不把昵称/个性当作品种知识。
- 保存会话，允许查看历史；AI 服务暂时不可用时，用户仍能查看监测、规则提醒与已有记录。
- 不因一次建议自动写入「已浇水」等已完成事件；只有用户确认并记录后才成立。

验收：更换植物、浇水记录或数据场景后，回答体现相应上下文；资料来源能追溯到实际检索到的知识条目，不能凭空生成引用。

### 2.6 照片异常辅助分析

- 上传或拍摄植物照片，结合当前植物档案、环境数据与养护记录辅助分析异常。
- 呈现可见现象、若干可能原因、下一步检查与处理建议；证据不足时要求补充叶片背面、整株、土壤等照片或养护信息。
- 叶黄、叶斑、萎蔫可能有多种原因；不能把单张照片直接等同于确诊病害。
- 分析结果可保存到成长记录，再次查看时保留照片、时间、用户描述和分析依据。
- 照片辅助识别品种可作为增强项；本次必须的是异常辅助分析。档案创建先允许用户在小型植物目录中手动选择，避免把自动识别作为所有流程的前置依赖。

验收：可完成上传 → 分析 → 查看建议 → 保存记录；无关或模糊照片能得到合理提示，不编造确定诊断。

### 2.7 长期数据总结

- 按用户选定周期生成养护总结，建议先做按需周报，不依赖复杂定时任务。
- 程序先统计数据覆盖时长、缺失情况、温湿度范围、光照变化、提醒及养护次数；AI 再解释。
- 说明总结周期与数据覆盖情况；有 7 天跨度但只收到少量读数，不能写成连续监测了 7 天。
- 说明观察到的变化和下阶段关注事项；没有照片或生长测量时，不断言「长高了」「长出新叶」或「根系恢复」。
- 可以用标记为模拟的历史数据演示长期总结，但不能把演示历史伪装成用户的真实种植经历。

验收：总结中的浇水次数、时间范围和关键数值与程序统计一致，且能在记录与曲线中核对。

### 2.8 简化账号、设备与同步

- 使用唯一账号和密码完成注册、登录、退出及恢复登录状态；无需邮箱、短信或第三方身份验证，一个账号管理自己的植物和记录。
- 所有私有植物、照片、会话与设备数据按账号归属访问；没有社交不等于所有账号共用一份私有数据。
- 提供虚拟花盆绑定、命名、解绑和关联植物；一个设备同一时刻只对应当前绑定的植物，历史测量保留当时的归属。
- 展示模拟连接状态、最后同步时间及数据来源。
- 网络设置在本版只涉及应用可联网状态与模拟设备状态；真实 Wi-Fi 配网、蓝牙发现、固件升级等暂缓。
- 服务端持久化档案、养护事件、历史数据与会话；刷新、重新登录或换浏览器后可恢复。先不做离线编辑冲突合并。
- 隐私设置至少说明照片/聊天会被发送给 AI 服务，并提供删除相关记录与用户数据的路径；保存范围随实现明确。

验收：登录后能恢复本账号的数据；解绑不串改历史记录；应用网络中断时能说明当前状态，不能把「服务器可访问」混同于「设备在线」。

## 3. Mock 的最小要求

模拟数据应复现可理解的场景，而不是四个互不关联的随机数：

- 正常日夜：照度有日夜周期，温湿度在合理范围内变化，土壤含水指数逐步降低。
- 缺水：土壤持续变干，可触发检查提醒。
- 刚浇水：用户产生事件，在模拟器中呈现水分上升和后续缓慢下降。
- 光照偏低：连续白天时段缺少足够光照，而不是单独降低一个瞬时值。
- 数据异常：设备离线、单一传感器缺失、过期读数或异常尖峰。

实现建议：提供同一时间轴的历史回放和实时续写，固定场景可重复复现。传输方式可后定，业务层只依赖统一的观测数据，不预绑定 MQTT、蓝牙或某个硬件 SDK。

## 4. 最小页面组成

这是信息组织建议，不是已确定的 UI 设计：

1. 登录/注册。
2. 我的植物与新建档案。
3. 植物主页：状态、提醒、最近记录、快捷操作。
4. 环境详情：历史曲线和趋势。
5. 养护记录：时间线、补记与照片。
6. AI 助手：问答、照片分析、阶段总结，可共用植物上下文。
7. 设备与设置：虚拟设备、连接状态、同步、通知与隐私。

## 5. 当前开发计划

用户确定的当前顺序为：工程搭建 → 账号密码注册登录 → 用户植物档案录入 → 权威植物知识资料整理与项目内保存。以下细化为各步的目标与验收建议。Flutter 工程在 `app/`，Spring Boot 工程在 `backend/`，容器编排在 `deploy/`。PostgreSQL 位于服务器 `8.155.138.61`。账号密码注册登录已实现；植物档案尚未实现。

### 第一步：工程搭建

- 在 `app/` 创建 Flutter 示例工程，支持 iOS 与 Android。
- 在 `backend/` 创建 Spring Boot 工程，配置 PostgreSQL 连接与数据库迁移。
- 连接服务器 `8.155.138.61` 上的 PostgreSQL，准备配置示例与启动说明，真实凭据不提交。
- 建立一个用于连通验证的后端接口，让 Flutter 能实际访问后端；手机/模拟器地址按运行环境配置。
- 验收：客户端能启动，后端能启动并连接数据库，Flutter 能显示后端返回的数据；未验证的平台单独说明。

### 第二步：账号密码注册登录

- 实现注册、登录、退出、当前用户查询和登录状态恢复；不引入邮箱或短信验证服务。
- 明确账号的长度、允许字符和大小写规则；建立统一的账号规范化方式，并对规范化结果添加数据库唯一约束。
- 密码以适当算法哈希保存，不以明文或可逆加密保存；密码输入不做改变其含义的静默处理。
- 并发注册相同账号时，仅允许一个成功，其余请求返回可识别的账号占用错误。
- 受保护接口校验登录状态，登录凭据在 App 中安全存储。登录会话使用有效期 7 天的 JWT，服务端保存当前令牌，退出后该令牌失效。
- 验收：注册后可登录，重复账号被拒绝，错误密码登录失败，未登录不能访问用户数据，退出后当前登录凭据失效。

### 第三步：用户植物信息录入

- 完成植物创建、列表、详情、编辑和删除，数据归属从登录身份确定。
- 基础字段包括昵称、品种名称、种植日期或开始养护日期、摆放位置和备注；个性描述可选。
- 此阶段使用示例品种或手工填写名称，允许填写未知品种，不依赖真实传感器、照片识别或外部知识接口。
- 预留可空的标准物种关联；第四步建立知识目录后，再通过明确选择关联物种，不能把用户填写的文本直接当作经过核对的分类结果。
- 示例档案也通过真实接口保存到 PostgreSQL，退出并重新登录后仍能查看。
- 验收：用户可管理自己的多株植物；其他账号无法读取、修改或删除这些植物；日期未知时可正常保存。

### 第四步：获取权威植物知识资料并保存在项目中

- 来源与许可核查可与前面步骤并行，正式整理和导入在本步骤完成。
- 先覆盖约 5–10 种常见室内植物；种子名单在整理时明确，不以全量全球分类导入作为启动条件。
- 物种名称与分类优先核查 WFO 等可下载资源；养护知识结合大学推广机构或园艺机构的资料，逐条确认适用条件和再利用范围。
- 采用可版本管理的 JSON 等结构化文件保存物种、知识条目和来源清单，提供可重复执行的导入方式写入 PostgreSQL。
- 示例组织可为 `data/plant-knowledge/` 下的物种、养护知识、来源与许可文件；这是后续实施建议，当前目录尚未创建。
- 保存原始来源标识、链接、版本/访问日期、许可及必要署名；权威来源事实与本项目整理、翻译或模型生成的文字分别标记。
- 许可明确允许保存和再分发的资料可以随项目提交；授权不明确的全文和图片只保留引用信息，不直接整站复制。
- 验收：知识文件可核对出处，导入可重复执行且不会重复增加条目，可按标准物种查询分类资料与养护信息；授权未确认或缺失的部分明确标记。

这四步完成后，再按完整 MVP 范围实现环境数据模拟、曲线、规则提醒、养护事件、AI 问答、照片分析及阶段总结；这些功能仍属于项目范围。

## 6. 已确认选择与后续决定

已确定使用 Flutter、Java / Spring Boot 和 PostgreSQL。AI 框架与模型接入依据见 [技术选型说明](./technology-selection.md)；具体模型厂商、依赖版本、真实设备协议和最终养护数值阈值尚未确定。

建议首版优先覆盖约 5–10 种常见室内植物；具体名单、演示物种与最初规则配置在开发前落实。音乐和社交不进入本版数据与页面的验收范围。

资料与竞品依据见 [植物资料与参考产品核查](./plant-knowledge-and-products.md)。
